An operational technology security assessment needs a clear boundary. The same test activity can be appropriate in a lab and unsuitable on a production control network. A useful scope makes those differences explicit before work begins.

## Start with the environment

Record which sites, network zones, system types, and interfaces are included. Note dependencies between control systems and supporting services, and identify any systems that must remain out of scope.

The inventory does not need to be a perfect asset register to be useful. It should make the assessment boundary understandable to the people who operate the environment.

## Agree on operating constraints

Discuss permitted test windows, access methods, change controls, safety requirements, and contacts for operational coordination. Clarify which activities require advance notice or explicit approval, and how testing will pause if an unexpected condition appears.

## Choose methods that fit the scope

Different methods have different operational effects. Passive review, configuration inspection, lab testing, and active network testing should be considered separately. The selected approach should match the agreed objectives and system constraints.

## Make the output actionable

Findings are easier to use when each one describes the affected asset or zone, the observed condition, the evidence, and a practical next step. Keep assumptions and untested areas visible so readers can tell what the assessment did and did not cover.

## Before work begins

- Confirm asset and network boundaries.
- Record prohibited actions and operational windows.
- Name the people who can approve, pause, or resume testing.
- Agree how evidence and findings will be handled.
- Review the scope with both security and operations stakeholders.

A clear scope helps teams discuss security work in terms of their actual environment, not a generic test plan.
